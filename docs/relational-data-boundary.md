# 關聯式病歷原始資料：目前能力界線

2026-10-12，核對 RDE `db39967` 與 Workbench `79975c7`。

**RDE 尚未提供完整的多表病歷關聯與研究族群建構契約。** 既有配對、重複量測與長格式縱向方法處理已載入的一份資料表；這不代表病人、就醫、檢驗、診斷、用藥原始表已被正確串聯。原生計畫的來源引用與執行收據，也不能證明主外鍵、時間窗及個案分母正確。

## 實際檢查

- [run_intake](../src/rde/interface/mcp/tools/discovery_tools.py) 掃描多檔，但只載入第一個可用檔；未載入檔與未選取候選工作表保存為 `partial_raw_coverage`。這是覆蓋範圍提醒，不是 relational join。
- `load_dataset` 可明確載入其他表；單獨載入並沒有建立表之間的主外鍵、基數或研究族群規則。
- Live MCP 72 個工具的 schema 與實作盤點，未找到一般病歷關聯／cohort 建構介面。
- [生存 preflight](../src/rde/infrastructure/clinical/survival.py) 在提供 `subject` 時拒絕缺失或重複 ID；未提供此欄位時，`independent_rows=true` 仍是宣告，不是從資料證明獨立性。

真實 stdio MCP 測試使用完全合成的四表：12 名受試者、24 筆就醫、18 筆檢驗、9 筆用藥；檢驗刻意含部分對應、不存在的 ID 與空鍵。第一個被收件載入的檔案是用藥表，另三檔列為未覆蓋，不能依檔名假設病人表會先載入。明確載入病人表後 preflight n=12；就醫表指定 `subject_code` 時拒絕重複，不指定時接受並回報 n=24。沒有執行統計模型。

Workbench 服務層用真實 RDE 重現同一行為，並確認四份收件後，內建臨床計畫仍只綁定所選的一份來源。既有 pipeline source 6 項、genomics 14 項測試通過，只能證明其原定的來源治理及專用配對功能。

## 需要新增的正式契約

1. 固定來源集合、每表角色／資料粒度、主鍵／複合鍵／外鍵及 ID 字串規則。
2. 驗證 1:1／1:N／N:1／N:M 的基數、空鍵、衝突、未配對、重複匯出與預期列數；區分表的追加與欄位串聯。
3. 草擬並固定研究單位、index date、基線／追蹤窗、納排、事件定義、單位及彙總規則。部分連結不自動當陰性或自動排除。
4. 先保存連結品質與個案流程審閱，再產生有逐列／逐值來源追溯的分析資料集，將準備版本、來源集合、結果 hash 綁入既有計畫核准與恢復契約。
5. 以已知答案資料、獨立 SQL／參考實作、破壞測試、重啟，以及真實去識別資料的資料管理者核對驗收；程式成功執行或報告稽核通過均不足以取代這些檢查。

這是待實作的核心資料準備層，不是新增任意 merge 指令即可完成的功能。Agent 可提出候選鍵與規則，但不能自行猜測未知識別意義、時間窗或未連結資料的臨床意義。現階段不能宣稱直接上傳關聯式病歷原始匯出，即可完整自動分析。
